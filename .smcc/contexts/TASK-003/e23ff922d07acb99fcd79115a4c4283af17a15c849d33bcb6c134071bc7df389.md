# SMCC Context: TASK-003

## Task

TASK-003 (v5) — Context compiler with provenance frontmatter

## Goal

Implement the deterministic context compiler: given a task, produce a Markdown context package under .smcc/contexts/ containing exactly the explicit selection set, with YAML frontmatter provenance and a content_hash that excludes volatile fields.

## Acceptance Criteria

- Compiling a task twice against unchanged inputs yields an identical content_hash.
- Frontmatter records (id, version) for every authoritative object consumed and the ids of accepted dependency results.
- The compiled body contains only the explicit selection set defined in CON-003.
- Content ordering is stable across runs.
- Changing one referenced object's version changes the hash and the changed input is identifiable from provenance.

## Project Goal

### GOAL-001 (v1) — Build the SMCC v1 vertical slice

Build the first usable SMCC vertical slice: explicit authoritative project state, a task DAG, deterministic task-specific context compilation with provenance, structured agent results, state-change proposals, human accept/reject transitions, and dependency-aware invalidation — all file-backed, diffable, and inspectable in the repository. The smcc repository manages itself with this system as it is built.

## Relevant Constraints

### CON-001 (v2) — Python is the primary implementation language

Primary implementation language is Python. TypeScript is acceptable only where it provides concrete value for VS Code integration. Other languages require a compelling reason.

### CON-002 (v2) — File-backed authoritative state; no database in v1

Authoritative state is stored as YAML/JSON files in the repository. Do not introduce a database unless a demonstrated requirement makes the file-backed model untenable. State must remain transparent, human-readable, diffable, and version-controllable.

### CON-003 (v2) — Context selection is explicit only in v1

Do not implement automatic relevance inference, tag matching, embeddings, semantic search, or LLM-selected context. Compiled context contains only: the task itself; its acceptance criteria and task-local constraints; the project goal; project-scoped constraints; objects named by the task's context_refs; and the accepted Result of each task dependency, as named by that task's accepted_result field.

### CON-004 (v2) — v1 scope exclusions (deferred work)

Do not implement in v1: multi-agent orchestration; autonomous planning; model routing; remote service architecture; vector databases; policy engines; production MCP integration; full UI; database-backed state; distributed execution; sophisticated migration infrastructure; grouped proposal transactions or partial acceptance; collision-free distributed ID allocation. Build the complete state lifecycle first.

### CON-005 (v2) — Agents propose; humans accept consequential state transitions

Consequential authoritative state must not silently change because an agent emitted prose or modified a file. Agent output flows through structured results and proposals to explicit human accept/reject transitions. During bootstrap this is a workflow convention, not a technical enforcement; do not claim otherwise.

## Relevant Decisions

### DEC-003 (v1) — Dual dependency model on tasks

Tasks distinguish task_dependencies (DAG ordering and dependency-result relationships) from context_refs (authoritative state required for the task). Compiled-context provenance records the exact object and version actually consumed.

### DEC-004 (v1) — Compiled-context provenance lives in YAML frontmatter

Compiled Markdown contexts include YAML frontmatter recording task id and version, compiler version, the (id, version) of every authoritative state object consumed, dependency result ids, a content_hash, and a compiled_at timestamp. No separate context-manifest file in v1.

### DEC-005 (v1) — Deterministic compilation and content_hash semantics

Given the same task version, referenced state-object versions, accepted dependency results, compiler version, and selection rules, SMCC produces the same semantic context and content_hash. Generated content uses stable ordering. content_hash is computed over canonical generated content excluding volatile fields (compiled_at, content_hash). A compiled context is stale when any recorded input version or accepted dependency result no longer matches the currently authoritative input, and the changed input must be identifiable.

### DEC-006 (v1) — Compiled contexts are committed to Git in v1

Compiled contexts are retained and committed because they form the inspectable record of exactly what context was supplied to an agent. May be revisited after deterministic reconstruction is demonstrated reliably.

## Dependency Outputs

### RESULT-001 — accepted result of TASK-001

Implemented the typed v1 SMCC object model (Pydantic) and the file-backed store. The store loads, validates, and round-trips the repository's own bootstrap fixture; 30 tests pass.

Findings:

- Pydantic's discriminated union on the type field gives exact typed parsing of heterogeneous state directories with no per-directory dispatch logic.
- YAML round-trips are semantically stable but not byte-identical (block-scalar style and key quoting are not preserved); the round-trip acceptance criterion is met at model equality, which is the correct level per DEC-001 since Git diffs remain readable.
- Result immutability (DEC-007) was enforceable almost for free at the store layer by refusing to overwrite an existing Result file.

Unresolved questions:

- Task status 'blocked' vs 'ready' is stored but derivable from the DAG; TASK-002 will need a decision on whether validate flags drift between stored status and derived readiness.
- Timestamp granularity is date-only in the fixture; datetime may be wanted once transitions are machine-executed.
