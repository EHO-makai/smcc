# SMCC Context: TASK-004

## Task

TASK-004 (v2) — Staleness detection for compiled contexts

## Goal

Implement staleness detection per DEC-005 and ARCHITECTURE section 12.1: given a compiled context's provenance frontmatter, determine whether any recorded input (task version, state-object version, or dependency accepted result) no longer matches the currently authoritative input, and identify exactly which inputs changed.

## Acceptance Criteria

- A freshly compiled context checked against unchanged inputs is reported fresh.
- Bumping a recorded state object's version reports the context stale and identifies that object with its recorded and current versions.
- A dependency whose accepted_result no longer matches the recorded result id reports the context stale and identifies that dependency.
- A recorded input that no longer resolves in authoritative state reports the context stale and identifies the missing input.
- The CLI reports staleness for each compiled context of a task and distinguishes fresh from stale via exit code.

## Project Goal

### GOAL-001 (v1) — Build the SMCC v1 vertical slice

Build the first usable SMCC vertical slice: explicit authoritative project state, a task DAG, deterministic task-specific context compilation with provenance, structured agent results, state-change proposals, human accept/reject transitions, and dependency-aware invalidation — all file-backed, diffable, and inspectable in the repository. The smcc repository manages itself with this system as it is built.

## Relevant Constraints

### CON-001 (v2) — Python is the primary implementation language

Primary implementation language is Python. TypeScript is acceptable only where it provides concrete value for VS Code integration. Other languages require a compelling reason.

### CON-002 (v2) — File-backed authoritative state; no database in v1

Authoritative state is stored as YAML/JSON files in the repository. Do not introduce a database unless a demonstrated requirement makes the file-backed model untenable. State must remain transparent, human-readable, diffable, and version-controllable.

### CON-003 (v3) — Context selection is explicit only in v1

Do not implement automatic relevance inference, tag matching, embeddings, semantic search, or LLM-selected context. Compiled context contains only: the task itself; its acceptance criteria and task-local constraints; the project goal; project-scoped constraints; objects named by the task's context_refs; and the accepted Result of each task dependency, as named by that task's accepted_result field. Status semantics: the automatic inclusion of project-scoped constraints applies only while they are authoritative (retired constraints are excluded); an object explicitly named by context_refs or task constraints is included regardless of its status, and provenance records exactly what was consumed.

### CON-004 (v2) — v1 scope exclusions (deferred work)

Do not implement in v1: multi-agent orchestration; autonomous planning; model routing; remote service architecture; vector databases; policy engines; production MCP integration; full UI; database-backed state; distributed execution; sophisticated migration infrastructure; grouped proposal transactions or partial acceptance; collision-free distributed ID allocation. Build the complete state lifecycle first.

### CON-005 (v2) — Agents propose; humans accept consequential state transitions

Consequential authoritative state must not silently change because an agent emitted prose or modified a file. Agent output flows through structured results and proposals to explicit human accept/reject transitions. During bootstrap this is a workflow convention, not a technical enforcement; do not claim otherwise.

## Relevant Decisions

### DEC-004 (v1) — Compiled-context provenance lives in YAML frontmatter

Compiled Markdown contexts include YAML frontmatter recording task id and version, compiler version, the (id, version) of every authoritative state object consumed, dependency result ids, a content_hash, and a compiled_at timestamp. No separate context-manifest file in v1.

### DEC-005 (v1) — Deterministic compilation and content_hash semantics

Given the same task version, referenced state-object versions, accepted dependency results, compiler version, and selection rules, SMCC produces the same semantic context and content_hash. Generated content uses stable ordering. content_hash is computed over canonical generated content excluding volatile fields (compiled_at, content_hash). A compiled context is stale when any recorded input version or accepted dependency result no longer matches the currently authoritative input, and the changed input must be identifiable.

## Dependency Outputs

### RESULT-003 — accepted result of TASK-003

Implemented the deterministic context compiler: compile_context builds the explicit CON-003 selection set from a snapshot, renders a stable-ordered Markdown context package with DEC-004 YAML provenance frontmatter, and computes a sha256 content_hash over canonical content excluding volatile fields (DEC-005). write_context stores the package content-addressed under .smcc/contexts/<task-id>/<content_hash>.md. The compiler compiled its own task's context, which is committed per DEC-006. 67 tests pass.

Findings:

- Content addressing by content_hash makes write idempotence trivial and collision-safe - a same-named file is by construction the same context, so no overwrite handling is needed.
- Retired project-scoped constraints are excluded from the always-include rule (they are no longer authoritative); an explicitly named retired object via context_refs is still included because explicit naming wins. CON-003 does not state this; flagged below.
- Windows forbids colons in filenames, so content_hash is bare hex with no algorithm prefix; the algorithm is fixed by compiler_version.
- Living-fixture lesson (fourth occurrence) - flipping TASK-003 to in_progress broke a validate drift test that relied on the live fixture's status; the test now seeds its own statuses.

Unresolved questions:
